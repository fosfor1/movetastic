# Weekly Training Load Implementation Plan

## Overview

Roadmap slice S-02 (US-01 AC "Ekran główny pokazuje wyliczone obciążenie treningowe z ostatnich 7 dni jako konkretną liczbę", input to FR-003): a signed-in runner sees on `/dashboard` their training load from the last 7 days as a single integer that updates after they add a workout. This plan settles the roadmap's blocking unknown (Open Question 3, load formula and scale) as **load = Σ (distance_km × avg_heart_rate / 100)** over the S-01 window, so that the "e.g. 100" threshold S-03 will use means a genuinely heavy amateur week (~70 km at HR ~145).

## Current State Analysis

- `/dashboard` already loads exactly the workouts this slice needs: `listRecentWorkouts(supabase, todayInAppTimeZone())` (`src/pages/dashboard.astro:17`) returns the user's workouts dated today−6…today in Europe/Warsaw (`src/lib/dates.ts:28`), each with `distance_km` (number) and `avg_heart_rate` (`src/lib/workouts.ts:38-46`).
- Isolation is enforced by RLS on `public.workouts` (`supabase/migrations/20261003120000_create_workouts.sql:15-27`), so a value computed from that list only ever covers the signed-in user's workouts.
- The DB `CHECK` constraints bound inputs (distance 0.1–200, HR 30–230), so every workout contributes a positive, finite amount.
- On a list error the dashboard sets `listError` and renders an error message instead of the list (`src/pages/dashboard.astro:13-20,66-67`).
- The only automated check is `scripts/smoke.mjs`. It signs up user A, saves exactly one valid workout (today, a unique distance `1XX.YZ` km, HR 150; `scripts/smoke.mjs:34-37,74-78`), and asserts that user B sees the empty state (`scripts/smoke.mjs:135-139`). Its step expectations support `status`, `location`, `bodyIncludes` and `bodyExcludes` only (`scripts/smoke.mjs:148-163`).
- There is no unit test suite. The CI gate is `npx astro sync && npm run lint && npx astro check && npm run build`, and CI also runs smoke.

## Desired End State

- `/dashboard` shows a card "Obciążenie z ostatnich 7 dni" with an integer (pl-PL formatting, rounded half-up) equal to `round(Σ distance_km × avg_heart_rate / 100)` over the workouts in the 7-day window. With no workouts in the window it shows `0`. A one-line hint explains the formula.
- After adding a workout and being redirected to `/dashboard`, the number includes the new workout. No separate refresh mechanism is needed, because the page is SSR.
- If the workout list fails to load, the load card is not rendered. The existing error message is the only feedback, so a false `0` never appears.
- The unrounded value is available from a pure, framework-free function that S-03 will compare against its threshold. Known boundary mismatch handed to S-03: a load of, for example, 99.6 is displayed as `100` but is below a threshold of 100. S-03 must either compare against the rounded value or explicitly accept this mismatch.
- `npm run smoke` proves that user A's dashboard shows the expected load for their one workout and that user B's shows `0`.

### Key Discoveries:

- No new query, migration or RLS change is needed. The load is a pure fold over the list the dashboard already fetches (`src/pages/dashboard.astro:17`).
- Smoke's single valid workout for A has HR 150, so its expected load is `round(distanceKm × 1.5)`, which falls between 150 and 300. Distances generated by smoke are `H/100` with a non-zero last digit of H. An exact `.5` needs H to be a multiple of 100, so rounding ties never occur in smoke.
- A 3-digit number can appear elsewhere in the HTML, so the smoke assertion must be anchored to a marked element rather than a bare substring.

## What We're NOT Doing

- The today's-suggestion flow, the "sugestia na dziś" button and the threshold comparison (S-03).
- Per-user thresholds or personalised formulas (Roadmap Open Question 2). There is one global formula.
- Richer inputs such as pace, duration, terrain or perceived effort (Roadmap Open Question 1).
- Storing or caching the load in the database. It is computed on every dashboard render.
- A unit test framework such as Vitest. The test strategy belongs to Module 3, and smoke covers this slice.
- Showing a "—" or explanatory empty state instead of `0` when there are no workouts.
- Editing workouts (FR-005, parked).

## Implementation Approach

Add one pure module, `src/lib/training-load.ts`, that computes the unrounded weekly load from a list of workouts. The dashboard calls it on the workouts it already has and renders the rounded value in a card above "Dodaj trening". Rounding happens only at display time, so S-03 compares the exact value. Smoke gains a regex body expectation and two load assertions (A = expected, B = 0), and a manual deploy ships the change. There is no migration, so no DB step is needed before deploy.

## Critical Implementation Details

- **Debug & observability**: Smoke locates the load through the `data-testid="weekly-load"` element, whose only text content is the formatted number. Smoke reimplements the formula and formatter, because it cannot import TypeScript. Changing the formula, the rounding/format or that marker requires updating `scripts/smoke.mjs` in the same commit, as was already done for the distance format in S-01.

## Phase 1: Load calculation and dashboard display

### Overview

Introduce the training-load function and show its result on the main screen.

### Changes Required:

#### 1. Training-load module

**File**: `src/lib/training-load.ts` (new)

**Intent**: Single source of truth for the load formula. S-02 uses it for display, and S-03 will use it for the threshold comparison. It is a pure function with no `astro:*` imports, so it is usable anywhere, following `src/lib/dates.ts`.

**Contract**: `export function weeklyTrainingLoad(workouts: Pick<Workout, "distance_km" | "avg_heart_rate">[]): number` returns `Σ distance_km × avg_heart_rate / 100`, unrounded, and `0` for an empty array. The caller is responsible for passing only the workouts in the 7-day window. A short header comment states the formula, its scale (10 km at HR 150 = 15) and that rounding is a display concern.

#### 2. Dashboard load card

**File**: `src/pages/dashboard.astro`

**Intent**: Show the load as a concrete number on the main screen (US-01 AC) between the signed-in header and the "Dodaj trening" button, in the existing glass-card style.

**Contract**:
- Compute `weeklyTrainingLoad(workouts)` only when `listError` is null. When `listError` is set, the card is not rendered.
- Card content: label `Obciążenie z ostatnich 7 dni`, the value formatted with `new Intl.NumberFormat("pl-PL", { maximumFractionDigits: 0 })` inside an element carrying `data-testid="weekly-load"` that contains nothing but the number, and the hint `Suma z treningów: dystans (km) × średnie tętno ÷ 100`.
- No workouts in the window renders `0`.

#### 3. Roadmap decision record

**File**: `context/foundation/roadmap.md`

**Intent**: Record that this change resolved the load formula, so S-03 planning no longer sees it as a blocker.

**Contract**: Mark Open Roadmap Question 3 as resolved, with the formula and a link to this plan. In the S-02 slice, mark the Unknowns entry as resolved and set its `Block:` to `no`. Update the S-02 Backlog Handoff note. Leave the `Status` fields untouched, because `/10x-plan`, `/10x-implement` and `/10x-archive` own them.

### Success Criteria:

#### Automated Verification:

- CI gate passes: `npx astro sync && npm run lint && npx astro check && npm run build`

#### Manual Verification:

- On `npm run dev`, a user with no workouts in the window sees the card with `0`.
- After adding 10 km at HR 150 the card shows `15`; after also adding 5,5 km at HR 140 it shows `23` (15 + 7,7 = 22,7).
- A workout dated 7 days ago (today−7) does not change the number, and one dated today−6 does.
- The card is readable on an Android-width viewport (~360 px) and sits above "Dodaj trening".

## Phase 2: Smoke verification and production rollout

### Overview

Lock the formula and per-user isolation of the load into the CI smoke test, then deploy.

### Changes Required:

#### 1. Smoke regex expectation

**File**: `scripts/smoke.mjs`

**Intent**: Allow a step to assert on a pattern so the load number can be matched inside its marked element without colliding with other numbers in the page.

**Contract**: Add an optional `bodyMatches: RegExp` to step expectations. On a mismatch, the step reports `expected body to match <regex>` in the same style as the existing checks.

#### 2. Load assertions

**File**: `scripts/smoke.mjs`

**Intent**: Prove the formula end to end for user A and prove that B's load does not include A's workout.

**Contract**:
- Compute `loadDisplay = new Intl.NumberFormat("pl-PL", { maximumFractionDigits: 0 }).format(distanceKm * 150 / 100)` next to `distanceDisplay`, with a comment saying it mirrors `src/lib/training-load.ts` + `src/pages/dashboard.astro`.
- The step "A: dashboard lists the new workout" (or a new step right after it) additionally expects `bodyMatches` for `data-testid="weekly-load"[^>]*>\s*<loadDisplay>\s*<`.
- The step "B: dashboard shows empty state, not A's workout" additionally expects the same pattern with `0`.
- Update the header comment to mention the training-load check.

#### 3. Production rollout

**Intent**: Ship to Cloudflare Workers using the existing manual deploy (`context/deployment/deploy-plan.md`). No migration is involved, so there is no `db push` step.

**Contract**: No file changes, only the deploy action.

## Testing Strategy

### Unit Tests:

- None. No unit framework exists, and adding one is out of scope (Module 3). The formula is small and pure. Smoke checks it end to end, and the manual steps cover the window boundary and multi-workout sum.

### Integration Tests:

- Smoke: A with one workout shows `round(distance × 1.5)`; B shows `0` (isolation of the derived value).

### Manual Testing Steps:

1. Fresh user → card shows `0`.
2. Add 10 km at HR 150 → `15`.
3. Add 5,5 km at HR 140 → `23`.
4. Add a workout dated today−7 → number unchanged; today−6 → number increases.
5. Check layout at ~360 px width.

## Performance Considerations

The calculation is an O(n) fold over at most a week of the user's workouts, already fetched for the list. It adds no extra round trip and stays well within the 1–2 s NFR.

## Migration Notes

None. There are no schema changes, and existing workouts count immediately.
